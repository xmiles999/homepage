# 处理文件前的本地工作流：从原始文件到可交付结果

文件处理最容易出问题的地方，通常不是某个按钮怎么点击，而是原始文件、临时结果和最终交付物混在了一起。无论使用桌面程序、命令行工具还是网页工具，都可以先建立一套不依赖具体产品的工作流。

## 1. 先保留原始文件

开始处理前，先复制一份原始文件，并把副本标记为“待处理”。不要直接在唯一文件上覆盖保存。这样即使转换失败、误删元数据或导出参数不合适，也能重新开始。

文件名应当能说明内容和状态，例如：

- `meeting-2026-09-12-original.wav`
- `meeting-2026-09-12-sample.mp3`
- `meeting-2026-09-12-final.mp3`

不要把密码、访问令牌或身份证明写进文件名。需要共享文件时，也应检查文件名是否泄露不必要的信息。

## 2. 先用小样本验证

不要一开始就处理全部文件。先截取一个短样本，验证格式、清晰度、时长、方向、编码和保存位置。样本验证通过后，再扩大到完整文件或批量任务。

小样本还有一个好处：失败时更容易定位原因。一次只改变一个变量，例如先确认输出格式，再调整质量参数，最后才尝试批量处理。

## 3. 把输入、过程和输出分开

可以使用三个目录：

- `original`：只读的原始文件；
- `working`：临时片段、中间结果和实验版本；
- `export`：已经通过检查、准备交付的文件。

处理过程中产生的缓存、下载文件和失败结果不应直接混入交付目录。目录分开后，清理临时文件和回溯处理步骤都会更简单。

## 4. 对结果做可观察的检查

不要只看“任务完成”或“下载成功”。应至少检查：

- 文件是否能够打开或播放；
- 时长、页数、尺寸或记录数是否符合预期；
- 文件大小是否异常；
- 内容是否出现截断、乱码、缺页或明显质量下降；
- 文件名、扩展名和实际格式是否一致。

如果文件要交给其他人或系统使用，再做一次目标环境测试。能够在自己的设备上打开，不代表接收方的软件一定能正确处理。

## 5. 记录一次成功的参数

完成任务后，记录输入类型、输出类型、关键参数、处理日期和检查结果。遇到同类任务时，先复用已经验证过的流程，而不是凭记忆重新试错。

记录不必复杂，一段简短文字就够：

> 输入：WAV，约 12 分钟；输出：MP3；检查：桌面播放器和手机均可播放；限制：大文件处理时间较长。

## 6. 交付前再做一次隐私检查

文件可能携带元数据、修订记录、隐藏页面、批注、缩略图或原始路径。公开发送前，应确认这些信息是否有必要保留。涉及客户资料、内部文档或个人信息时，优先使用组织批准的处理方式，并保留必要的操作记录。

这套流程的重点不是选择某个“最好”的工具，而是让原始文件可恢复、过程可解释、结果可检查。外部工具只能作为流程中的一个步骤，不能替代对文件和交付结果的判断。
